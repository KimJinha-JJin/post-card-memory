- **미검증:** 도착/혼합/비어 있음은 기존 데이터에 없어 만들지 않았어. 해당 상태의 순수 로직·문구는 JVM 검증이며 실제 그림 QA가 아니야.
- **코드 계산만 완료:** 320dp 폭이면 본문 종이 288dp, 글 영역 136dp, 그림 영역 x=16..122dp, 글 시작 x=124dp. 기본 종이 92dp+위 틈 24dp+손잡이 여유 약 74.249dp, 남은 높이 약 190.249dp 미만이면 종이를 구성하지 않아. 큰 글꼴은 종이 높이를 늘린 뒤 같은 판정을 써. 작은 화면·큰 글꼴의 실제 줄바꿈/가독성과 짧은 화면 숨김은 실기기 미검증이야. 기기 해상도·배율을 강제로 바꾸지 않았어.

- 디오라마 종이는 화면 폭−32dp×기본 92dp, 봉투는 84×48dp야. 달력 서랍은 304dp, 안쪽 좌우 여백 각 24dp로 종이 폭 256dp이며 높이는 달력 내용에 따라 정해져. 두 화면 모두 같은 종이를 비율 유지 cover-crop해서 ImageShader로 그리고, 소인·민트 봉인·테이프·엿보는 엽서는 코드로 그려. 추가 디오라마 전용 이미지 파일은 없어.
- 실제 resolved `androidx.compose.ui:ui-android:1.11.0`을 dependencyInsight로 확인하고 로컬 공식 sources JAR의 `ImageResources.android.kt`, `PainterResources.android.kt`, `AndroidImageBitmap.android.kt`를 읽었어. 달력과 디오라마 종이는 각각 `ImageBitmap.imageResource`를 remember하며, 봉투는 달력의 imageResource와 디오라마의 painterResource를 사용해. 이 경로들은 Coil 캐시가 아니라 Android `Resources.getDrawable`→BitmapDrawable의 Bitmap을 감싼 것이고, `asImageBitmap` 자체는 픽셀을 복사하지 않아. 달력 내부 여러 장은 전달받은 같은 ImageBitmap을 사용해.
- Android 공식 문서는 같은 리소스에서 만든 BitmapDrawable이 ConstantState의 Bitmap을 공유한다고 설명해: https://developer.android.com/reference/android/graphics/drawable/Drawable.ConstantState . **호출 지점이 둘이라는 사실만으로 Bitmap 두 개 또는 추가 decode를 확정할 수 없어.** 실제 개별 Bitmap identity·할당 stack·캐시 hit/miss는 측정하지 않았으므로 중복이 없다고도 단정하지 않아.
- 1122×1402×4 = 6,292,176바이트(약 6.001MiB)는 ARGB_8888 한 장을 가정한 산술값이며 실측 추가 RAM이 아니야. PNG 파일 크기와 decoded RAM은 별개야. PNG 무손실 압축은 같은 크기의 Bitmap RAM 절감 근거가 되지 않아.
- **판단 완료 — 수정하지 않음:** 반복 왕복 뒤 Bitmap 값은 회수돼 같은 수준으로 돌아왔고, 전체 PSS·Graphics도 계속 증가하지 않았어. 같은 픽셀의 불필요한 동시 복사나 6MiB 순증을 입증하지 못했어. 캐시 유지·일시 할당에 부합하는 관찰이지만 개별 회수 원인은 추적하지 않았어. 질감 손상·공용 달력 영향과 구현 복잡도를 감수할 효과가 확인되지 않아 이미지 교체·해상도 축소·공용 캐시 개편을 생략했어. 장시간 누수 부재의 증명은 아니야.
